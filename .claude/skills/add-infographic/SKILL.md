# インフォグラフィック作成アシスタント

公開済み（または下書き段階）の記事1本に、ヘッダー画像を1枚作って付ける。**記事は書かない**。書くのは `/write-post` の仕事。

**この画像の目的は「読みたいと思わせること」だけ**。記事の要約でも、詳細な資料でもない。厳密な数字を見せる場でもない。記事を開いた読者が最初の3秒で「自分に関係がある話だ」と分かればそれで役目は終わる。

このスキルの最大の失敗は**情報を詰めすぎること**。本文幅では約690pxまで縮むので、詰めた瞬間に何も読めない絵になる。詰めたくなったら削る。

## 前提の確認

`container system status` が `running` でなくても作業はできる（PNG化に Apple Container は使わない）。必要なのは次の2つで、どちらも入っている前提。

- Google Chrome（`/Applications/Google Chrome.app`）― ヘッドレスでHTMLをPNGに焼く
- ImageMagick の `magick` ― 減色と縮小確認に使う

無ければその場で書き手に伝えて中断する。代替手段を勝手に探さない。

## 使うファイル

| パス | 役割 |
|---|---|
| `infographics/template.html` | 2カラム型テンプレート。**これをコピーして中身を差し替える**（テンプレート自体は書き換えない） |
| `infographics/src/<記事スラッグ>.html` | 今回作る図のソース。`source: site` の外なので公開されない |
| `infographics/render.sh` | HTML → PNG。`./infographics/render.sh infographics/src/xxx.html` |
| `infographics/out/` | 焼いたPNGの置き場（gitignore済み） |
| `site/assets/img/posts/` | 公開するPNGの置き場 |

型は**2カラム型の1種類だけ**。カテゴリ別のテンプレートは今のところ作っていない。この型に載らない記事に当たったら、無理に押し込めず「この記事は今の型に合わない」と書き手に伝えて相談する（後述）。

## 破ってはいけない4つの制約

ここを外すと作り直しになる。毎回この4つを守る。

1. **画角は 1600 × 840（40:21）**。Chirpy のプレビュー枠が `aspect-ratio: 40/21` + `object-fit: cover` なので、16:9で作ると上下が3%ずつ切られてヘッダーとフッターが欠ける。OGP画像の 1200×630 も同じ比率なので、この1枚で両方まかなえる
2. **文字はキャンバス上19px以上**。本文幅で約8pxになる。これ以下は読めない
3. **収まらないときは文字を小さくせず、要素を削る**。載せる情報のかたまりは5〜8個まで
4. **図に書く事実は、すべて記事本文から取る**。記事に書いていない数字・断定を図で足さない。図だけ独り歩きしても嘘にならない状態を保つ

## 会話のしかた

- **1回のメッセージで聞くのは1問まで**。記事はもう書き終わっている。ここで疲れさせない
- 記事から読み取れることは**聞かずに自分で決めて、決めた結果を見せて確認を取る**。「どうしますか」ではなく「こうしました。直しますか」
- 各フェーズの冒頭で `[3/6 下書き]` のように現在地を示す

## フェーズ1: 対象の記事を決める

書き手が記事を指定していなければ、次を見て候補を出す。

```sh
ls site/_posts/ site/_drafts/ 2>/dev/null && ls site/assets/img/posts/ 2>/dev/null
```

- **画像がまだ付いていない記事**を優先する（front matter に `image:` があるかで判別）
- 下書き（`site/_drafts/`）でも作れる。ただし本文が固まっていないと作り直しになるので、下書きの場合は「本文はもう固まっていますか」と1問だけ確認する
- すでに `image:` がある記事を指定されたら、**作り直しなのか差し替えなのか**を確認する。既存のPNGを黙って上書きしない

対象が決まったら記事を全文読む。要約で済ませない。図に使う言葉は本文から取るので、原文を持っている必要がある。

## フェーズ2: 載せる要素を決める（ここが本体）

記事から次を拾い、**5〜8個のかたまりに絞った案を作って書き手に見せる**。この時点ではまだHTMLを書かない。

| テンプレートの位置 | 何を入れるか | 記事のどこから取るか |
|---|---|---|
| h1（2行） | 記事の結論。後半1行が蛍光ペンで強調される | タイトル、または冒頭1〜2文の結論部分 |
| lede（1文） | 誰のどんな問題を、どう片づける記事か | 冒頭の「この記事はこういう方に向けて書いています」の文 |
| badge | カテゴリと段階タグ | front matter の `categories` と段階タグ |
| 01 の3行 | 問題側。並べると差が見えるもの | 「揃っていない」「違う」を列挙している箇所 |
| 02 のプロンプト枠 | 記事の中心にあるプロンプト（2行まで） | 本文のコードブロック |
| 03 のカード2〜4枚 | 結果側。試した対象と、その一言 | 検証結果を並べている節 |
| footer | 釘を刺す一言と検証時点 | 「鵜呑みにしない」系の注意、検証月 |

**そのまま埋まらない記事のほうが多い。** 型に対して素材が足りない/余るときの判断はこう。

- **01 に並べるものが無い** → `.rows` ごと外して余白にする。無理に3行ひねり出さない
- **プロンプトが無い記事** → 02 の枠に、記事の核になる一文（判断基準・チェック項目）を入れる。`PROMPT` のラベルは適切な語に変える
- **カードが2枚しかない** → 2枚でよい。空欄を埋めるために記事にない項目を足さない
- **カードが5つ以上ある** → 記事で最も語られている4つに絞る。「他にもある」ことは図で表現しない
- **どこにも当てはまらない記事**（ニュース、比較表が主役の回など） → **正直に「この記事は今の型に合いません」と伝える**。型を歪めて1枚作るより、画像なしで公開するか、型を増やすかを書き手に決めてもらう

### 守秘と表記の確認（自分でやる。書き手に確認させない）

- 常駐先が特定できる記述を図に入れない。`writing-style.md` 4章の型で言い換える。**図は本文より拡散しやすい**（OGP画像としてSNSに出る）ので、本文より一段慎重に見る
- **絵文字は使わない**（`writing-style.md` 2章）。アイコンが要るならSVGで描く
- サービスのロゴ画像は使わない。ブランド色のドット1点と製品名テキストで表す
- 数字は記事に書いてあるものだけ。盛らない

案がまとまったら、**図に載る文言を箇条書きで全部書き出して見せる**。この時点で文言を確定させる。画像を作ってから文言を直すのが一番遠回りになる。

## フェーズ3: HTMLを作る

```sh
cp infographics/template.html infographics/src/<記事のファイル名から日付ごとスラッグ>.html
```

記事が `2026-08-24-check-ai-security-settings.md` なら `infographics/src/2026-08-24-check-ai-security-settings.html`。

`【】` で囲まれたプレースホルダを、フェーズ2で確定した文言に差し替える。**CSSは触らない**のが基本。触ってよいのは次だけ。

- カードの `dot` の色（対象サービスのブランド色）
- カード枚数を変えるとき（2枚なら `grid-template-columns: 1fr 1fr` のまま1行に、または `1fr` で縦2枚）
- 要素を削ったことで生じる余白の調整

フォントサイズを下げる方向の変更はしない。**入らないならフェーズ2に戻って要素を削る。**

## フェーズ4: 焼いて、縮めて、自分で見る

```sh
./infographics/render.sh infographics/src/<スラッグ>.html
```

出力は `infographics/out/<スラッグ>.png`（3200×1680、2倍解像度）。

**焼いたら必ず2回見る。** ここを飛ばすと、はみ出しや文字潰れに気づかないまま記事に載る。

1. **等倍で見る**（`Read` ツールでPNGを開く）― 要素が枠からはみ出していないか、フッターが切れていないか、左右のカラムの高さが極端に違わないか
2. **本文幅に縮めて見る**

```sh
magick infographics/out/<スラッグ>.png -resize 690x infographics/out/<スラッグ>-check.png
```

縮めたものを `Read` で開き、**すべての文字が読めるかを自分の目で判定する**。1つでも潰れていたら、フォントを上げるのではなく**その要素を削ってフェーズ3からやり直す**。

よく起きるはみ出しと対処:

| 症状 | 原因 | 対処 |
|---|---|---|
| フッターが下に切れる | 左カラムの中身が多い | `.rows` を1行減らす、プロンプトを1行にする |
| プロンプト枠が footer に重なる | 同上 | 同上 |
| カードの中で文字が2行に折れて詰まる | lead / desc が長い | 文言を短くする（記事の意味を変えない範囲で） |
| 右カラムだけ空きが目立つ | カード枚数と余白の不一致 | そのままでよい。埋めるために情報を足さない |

## フェーズ5: 記事に付ける

```sh
cp infographics/out/<スラッグ>.png site/assets/img/posts/<スラッグ>.png
```

記事の front matter に追記する（`tags` の下、`---` の上）。

```yaml
image:
  path: /assets/img/posts/<スラッグ>.png
  alt: 【画像の下にキャプションとして表示される一文】
```

- パスは `/assets/` から始める絶対パスでよい。Chirpy が `baseurl` を自動で付ける
- **`alt` は画像の下にキャプションとして表示される**。代替テキストであると同時に読者が読む文なので、「〜の図」ではなく、読んで意味の通る一文にする。図に書いていない情報をここで補ってよい
- ファイルサイズが 300KB を超えていたら書き手に伝える（減色で落ちない場合は要素が多すぎる可能性がある）

余裕があれば `./preview.sh` でローカル確認を勧める。**git 操作は提案するだけで実行しない**。

## フェーズ6: 終わり方

短く終える。

1. 作ったファイル（ソースHTML・PNG・front matterの差分）を**3行以内で**報告する
2. 本文幅で読めることを**自分で確認した**と明言する。確認していないなら言わない
3. 気づいたことがあれば1つだけ添える（型に合わなかった箇所、次に同じ型を使えそうな記事など）

ダークモードについては聞かれたら答える程度でよい。ヘッダー画像は1枚しか持てないのでテーマ切替に追従しない。テンプレートのクリーム地は黒背景でも刺さらないことを確認済み。本文中の画像であれば `{: .light }` / `{: .dark }` で2枚を出し分けられるが、ヘッダー画像では使えない。

## 型を増やしたくなったら

**その場で増やさない。** テンプレートが増えるほど保守が要る。2カラム型で数本回してから、どの型が本当に足りないかを見て決める。書き手から要望が出たら、次のどれに当たるかを一緒に確認する。

- 今の型で表現できないか（要素を入れ替えれば済むことが多い）
- その型を今後何本で使うか（1本のためのテンプレートは作らない）
- 増やすなら `infographics/template-<型名>.html` として並べ、このスキルの表に1行足す
