# 文体ガイド

「明日使える生成AI」の記事執筆時の文体・トーンをまとめたガイド。[content-strategy.md](content-strategy.md)で定めた対象読者（SES常駐のITエンジニア）・コンセプトを踏まえて執筆時に迷わないための基準とする。

- ステータス: ドラフト（v0.1）

---

## 1. 全体トーンの一言イメージ

**「同じ現場で働く先輩が、休憩中に『これ便利だよ』と教えてくれる」温度感。**

- 上から教える／講義する感じにしない（読者はITリテラシーがある前提なので、基礎の基礎から説明しすぎない）
- かといって仲間内のノリに寄せすぎない（技術ブログとしての信頼感は保つ）
- 「筆者が実際に現場で試して効果があった」という一次体験のトーンを軸にする

## 2. 基本ルール

| 項目 | 方針 |
|---|---|
| 文末表現 | です/ます調で統一する（だ/である調にしない） |
| 書き手の立ち位置 | 「筆者」として一人称視点で体験談を語る（客観解説一辺倒にしない） |
| 絵文字・カジュアル表現 | 本文・見出しとも基本的に使わない。**例外**: `AIにキャラクターを与えてみよう`シリーズなど、遊び要素が主目的の記事のみ許容 |
| 一文の長さ | 1文はできるだけ短く。「〜であり、〜のため、〜なので」と接続助詞で伸ばさず、句点で区切る |
| 体言止め | 見出し（H2/H3）では使ってよいが、本文では多用しない（読みやすさ優先） |

## 3. 一人称「筆者」の使い方

- **毎段落で使わない**。記事の導入（なぜこの記事を書くか）と、実体験ベースの具体例を出す箇所で使うのが基本
- 「筆者は〜だと感じました」のような感想の押し付けで終わらせず、必ず読者が真似できる手順・プロンプトに落とし込む
- 例:
  - ◎「筆者は客先の議事録作成にこのプロンプトを使い始めてから、清書の時間がほぼゼロになりました。」
  - △「議事録作成にはこのプロンプトが効果的です。」（悪くはないが、体験の裏付けがなく単なる解説文になりがち）

## 4. 読者への呼びかけ方

- 「あなた」は多用しない。「〜という方も多いのではないでしょうか」「〜という現場は少なくないはずです」のように、共感ベースの間接的な呼びかけにする
- 「みなさん」も使いすぎると講義口調になるため、記事の導入・まとめ程度に留める
- 読者を下に見た言い回し（「初心者の方でも」「難しく感じるかもしれませんが」の多用）は避ける。ITリテラシーがある前提なので、対等な実務者として書く

## 5. 専門用語・カタカナ語の扱い

- 読者はITエンジニアなので、一般的な技術用語（API、リポジトリ、トークンなど）は説明なしで使ってよい
- 生成AI特有の用語（ハルシネーション、コンテキストウィンドウ、ファインチューニングなど）は、`生成AIのきほん`シリーズで初出時に一言だけ補足する。それ以外のカテゴリでは説明を省略してよい（きほんシリーズへのリンクで代替する）
- 英語ツール名・機能名は基本カタカナ表記＋初出時のみ英語併記（例:「システムプロンプト（System Prompt）」）

## 6. コード・プロンプトの見せ方

- プロンプト例は必ずコードブロック（` ``` `）で囲み、地の文と区別する
- 「そのままコピペして使える」ことを重視し、変数部分は `【会議名】` のように分かりやすく明示する
- コード例にはコメントを最小限入れる（何をしているかより、なぜそうするかが分かる程度）

## 7. 避けたい表現

- 「絶対に」「必ず成功する」など、AIの出力を過信させる断定表現（ハルシネーションのリスクがある以上、過信を煽らない）
- 「〜するだけで一瞬で解決」のような煽り文句（ブログの信頼感を損なう）
- 特定の実在人物のモノマネ・誹謗中傷になりうる表現（`AIにキャラクターを与えてみよう`シリーズは「〇〇風」という一般的な話し方の再現に留め、実在の個人を模写しない）

## 8. カテゴリ別の微調整

| カテゴリ | トーンの微調整 |
|---|---|
| `生成AIのきほん` | 基本ルールに忠実に、噛み砕いた説明を意識する（Step1読者向け） |
| `プロンプト設計` / `業務効率化` / `ツール比較` | 「筆者の体験談」を最も色濃く出す。Before/Afterを必ず入れる |
| `Tips・小技` | テンポよく、結論を早く出す。前置きは短めに |
| `ニュース` | 事実部分は客観的に、影響・所感の部分で「筆者」視点を出す |
| `開発者向け` | 専門用語の補足を省略してよい。技術的な正確さを優先しつつ、である調にはしない |
| `AIにキャラクターを与えてみよう` | 例外的に遊び要素・カジュアルな言い回しを許容（文末は基本です/ます調を維持） |

## 9. チェックリスト（執筆後の確認用）

- [ ] です/ます調で統一されているか
- [ ] 「筆者」視点の実体験が最低1箇所は入っているか
- [ ] 断定しすぎる表現・煽り文句がないか
- [ ] 専門用語の説明過多・説明不足になっていないか（対象カテゴリのレベル感と合っているか）
- [ ] プロンプト・コード例はコピペしやすい形になっているか
