# 文体ガイド

「明日使える生成AI」の記事執筆時の文体・トーンをまとめたガイド。[content-strategy.md](content-strategy.md)で定めた対象読者（SES常駐のITエンジニア）・コンセプトを踏まえて執筆時に迷わないための基準とする。

- ステータス: ドラフト（v0.4、「AIが書いた文章に見せない」章を追加）

---

## 1. 全体トーンの一言イメージ

**「同じ現場で働く先輩が、休憩中に『これ便利だよ』と教えてくれる」温度感。**

- 上から教える／講義する感じにしない（読者はITリテラシーがある前提なので、基礎の基礎から説明しすぎない）
- かといって仲間内のノリに寄せすぎない（技術ブログとしての信頼感は保つ）
- 「筆者が実際に現場で試して効果があった」という一次体験のトーンを軸にする

## 2. 基本ルール

| 項目 | 方針 |
|---|---|
| 文末表現 | です/ます調で統一する（だ/である調にしない） |
| 書き手の立ち位置 | 「筆者」として一人称視点で体験談を語る（客観解説一辺倒にしない） |
| 絵文字・カジュアル表現 | 本文・見出しとも基本的に使わない。**例外**: `AIにキャラクターを与えてみよう`シリーズなど、遊び要素が主目的の記事のみ許容 |
| 一文の長さ | 1文はできるだけ短く。「〜であり、〜のため、〜なので」と接続助詞で伸ばさず、句点で区切る |
| 体言止め | 見出し（H2/H3）では使ってよいが、本文では多用しない（読みやすさ優先） |

## 3. 一人称「筆者」の使い方

- **毎段落で使わない**。記事の導入（なぜこの記事を書くか）と、実体験ベースの具体例を出す箇所で使うのが基本
- 「筆者は〜だと感じました」のような感想の押し付けで終わらせず、必ず読者が真似できる手順・プロンプトに落とし込む
- 例:
  - ◎「筆者は客先の議事録作成にこのプロンプトを使い始めてから、清書の時間がほぼゼロになりました。」
  - △「議事録作成にはこのプロンプトが効果的です。」（悪くはないが、体験の裏付けがなく単なる解説文になりがち）

## 4. 一次体験を、常駐先の具体を出さずに語る

読者の多くは客先常駐で働いており、筆者自身も同じ立場である。体験談はこのブログ最大の武器だが、常駐先の情報はほぼすべてが守秘の対象になる。「書けないから体験談をやめる」でも「うっかり書いてしまう」でもなく、**抽象度を上げて語る型**を持っておく。

原則: 守秘すべきなのは「**どこで・誰と・何のシステムか**」。読者に効くのは「**どんな状況で・何に困り・どうしたら・どう変わったか**」。前者を落として後者だけを書けば、体験の説得力はほとんど落ちない。

### 置き換えの型

| 書かない | 代わりに書く |
|---|---|
| 企業名・プロジェクト名・製品名 | 「常駐先」「ある現場」／規模感（「10名規模のチーム」） |
| 業種・事業が特定できる記述 | 業種に依存しない業務の型（「金融系基幹システムの改修」→「仕様変更の多い保守案件」） |
| 実際の議事録・仕様書・ログの引用 | 同じ構造のダミーを自作して載せる（形式だけ再現する） |
| 具体的な人物（「PMの〇〇さん」） | 役割だけ（「レビュー担当者」「PM」） |
| 現場固有のルール文面 | ルールの類型（「社外SaaSへの入力が全面禁止の現場」） |

- ダミーに置き換えた場合は、その旨を一言添える（例:「実際の議事録は載せられないため、同じ構造のサンプルに置き換えています」）。読者は事情を察するし、隠して装うより信頼される
- **数字は残す**。「清書が30分から5分になった」のような定量表現は、案件を特定しないうえに最も説得力がある。厳密な計測でなくてよいが、盛らない
- ツール名・モデル名は書いてよい（それ自体では現場を特定しない）。ただし「その現場で承認されていた」ところまで書くと導入状況の開示になりうるため、「筆者の環境では」程度に留める
- 迷ったら「**この記事を常駐先の担当者が読んだとき、自社のことだと分かるか**」を基準にする。分かってしまうなら抽象度を1段上げる

### そもそも現場の話が出せないとき

- テーマによっては、常駐先の話を一切出せないこともある。その場合は**自分の手元環境での検証**に置き換える。「業務で使った」でなくても「自分で試して確かめた」であれば一次体験として成立し、戦略ドキュメントの「机上の想像で書かない」方針は満たせる
- 「常駐先では使えなかったので、自宅で同等の環境を作って試した」という書き方は、むしろ同じ制約下にいる読者に刺さる

### 例

- ◎「筆者が入っていた保守案件では、社外SaaSへの入力が全面禁止でした。そこで社内で承認されていたツールだけで議事録の下書きを作る運用に切り替えたところ、清書の時間が半分以下になりました。」
- ✕「筆者が常駐している〇〇株式会社の基幹システム保守では、〇〇部の定例会議の議事録を……」（企業名・組織名が特定できる）
- ✕（実際の議事録をそのまま貼る）→ 同じ構造のサンプルを自作して貼る

## 5. 読者への呼びかけ方

- 「あなた」は多用しない。「〜という方も多いのではないでしょうか」「〜という現場は少なくないはずです」のように、共感ベースの間接的な呼びかけにする
  - ただし「〜ではないでしょうか」は**AIが書いた文章に最も出やすい言い回し**でもある。使うのは1記事に1回までとし、それ以上は言い切るか具体的な状況描写に置き換える（9章）
- 「みなさん」も使いすぎると講義口調になるため、記事の導入・まとめ程度に留める
- 読者を下に見た言い回し（「初心者の方でも」「難しく感じるかもしれませんが」の多用）は避ける。ITリテラシーがある前提なので、対等な実務者として書く
- 下限読者（AIの使い道がまだ見えていない層）向けの記事でも、**「初心者向け」「初めての方へ」とは書かない**。読者はITエンジニアであり、AI活用の経験が浅いことと初心者であることは別である。呼びかけるときは経験の浅さではなく**状況で呼ぶ**
  - ◎「まだ業務で使う機会がない方」「現場にAIが入っていない方」「何から試せばいいか決まっていない方」
  - ✕「AI初心者の方」「これから始める初心者向けに」

## 6. 専門用語・カタカナ語の扱い

- 読者はITエンジニアなので、一般的な技術用語（API、リポジトリ、トークンなど）は説明なしで使ってよい
- 生成AI特有の用語（ハルシネーション、コンテキストウィンドウ、ファインチューニングなど）は、`生成AIのきほん`シリーズで初出時に一言だけ補足する。それ以外のカテゴリでは説明を省略してよい（きほんシリーズへのリンクで代替する）
- 英語ツール名・機能名は基本カタカナ表記＋初出時のみ英語併記（例:「システムプロンプト（System Prompt）」）

## 7. コード・プロンプトの見せ方

- プロンプト例は必ずコードブロック（` ``` `）で囲み、地の文と区別する
- 「そのままコピペして使える」ことを重視し、変数部分は `【会議名】` のように分かりやすく明示する
- コード例にはコメントを最小限入れる（何をしているかより、なぜそうするかが分かる程度）

## 8. 避けたい表現

- 「絶対に」「必ず成功する」など、AIの出力を過信させる断定表現（ハルシネーションのリスクがある以上、過信を煽らない）
- 「〜するだけで一瞬で解決」のような煽り文句（ブログの信頼感を損なう）
- 特定の実在人物のモノマネ・誹謗中傷になりうる表現（`AIにキャラクターを与えてみよう`シリーズは「〇〇風」という一般的な話し方の再現に留め、実在の個人を模写しない）

## 9. AIが書いた文章に見せない

生成AIをテーマにしたブログの記事が、AIの出力そのままに見えてしまうと内容の説得力が落ちる。加えて、[content-strategy.md](content-strategy.md)1章の「公開前の一問」に照らせば、**AIが書けてしまう文章は、そもそも価値が出ていない**というサインでもある。この章は8章（避けたい表現）と目的が違う。8章は信頼を損なう表現を排除する話、この章は**書き手の固有性を残す**話である。

原則: 「AIっぽさ」の正体は**固有性の欠如**である。誰が書いても同じになる文は、AIにも書ける。逆に「いつ・どの環境で・何を試して・何が外れたか」が書いてある文は、AIには書けない。だから対処は言い回しを避けることだけでは足りず、**固有の情報を入れること**が本体になる（後半の「固有性を足す」）。

### 言い回しの癖

| 出やすい表現 | どうするか |
|---|---|
| 「〜ではないでしょうか」「いかがでしょうか」 | 5章で共感ベースの呼びかけとして挙げているが、最も目立つ癖でもある。**1記事に1回まで**。2回目以降は言い切るか、具体的な状況描写に置き換える |
| 「ぜひ試してみてください」（記事末の定型） | 締めは具体で終える。「まずは議事録1本で試すと違いが分かります」のように、何から試すかまで書く |
| 「〜と言えるでしょう」「〜と考えられます」 | 断定を避けたいなら、避ける理由のほうを書く。「筆者の環境では再現しなかったので、断定はできません」 |
| 「重要なポイントは3つです」 | 数を揃えるために内容を水増ししない。2つなら2つ、4つなら4つと書く |
| 「効率化」「最適化」「活用」など抽象名詞＋する | 何がどう変わるのかを動詞で書く。「議事録作成を効率化する」→「議事録の清書をやめる」 |
| 「〜を意識しましょう」「〜を心がけましょう」 | 心がけではなく手順を書く。心がけで終わる文は、たいてい書き手自身も実行していない |
| 「本記事では〜について解説します」 | [content-strategy.md](content-strategy.md)5章の共通ルールどおり、冒頭は「誰の・どんな悩みを解決するか」で始める |
| 「〜と言われています」 | 出典を書く。書けないなら文ごと消す |

### 構造の癖

- **すべてを均等に揃えない**。見出しごとの分量、箇条書きの項目の長さ、段落の長さが揃いすぎていると機械的に見える。書くことが多い箇所は長く、少ない箇所は短くてよい
- **メリット・デメリットを機械的に対で出さない**。片方しかないなら片方だけ書く
- **「まとめ」で本文の要約を繰り返さない**。まとめには本文になかったもの（次にやること、まだ分かっていないこと、次に読む記事）を書く
- **太字を1段落に何度も置かない**。すべてを強調することは、何も強調しないことと同じ
- **架空の人物・架空の事例を作らない**（「例えば、エンジニアのAさんは…」）。実際の体験を4章の型で抽象化して書く。抽象化と捏造は違う

### 固有性を足す

言い回しを直しても、中身が一般論のままなら結局AIが書ける文章になる。次のうち**最低1つ**を、記事の具体的な箇所に入れる。

- **いつ試したか** ―「2026年8月時点」「どのモデルで試したか」。AIの出力に時点は入らない
- **何が外れたか** ― うまくいかなかった試行、期待どおり動かなかった例。3章の一人称の使い方とも噛み合う
- **中途半端な数字** ―「清書が30分から5分になった」のような実測値。4章のとおり盛らない。丸めた数字（「約50%削減」「3倍速く」）はかえってそれらしく見えるので避ける
- **判断の理由** ― なぜその方法を選び、別の方法を選ばなかったのか

### AIに下書きさせる場合

下書きにAIを使うこと自体は問題ない。ただし**そのまま公開しない**。最低限、次を通す。

- **一次体験の段落は自分で書く**。AIが持っていない情報なので、書かせると一般論か、事実でない記述になる
- 上の表の言い回しを検索して潰す
- 声に出して読み、自分の話し方でない箇所を書き換える

## 10. カテゴリ別の微調整

| カテゴリ | トーンの微調整 |
|---|---|
| `生成AIのきほん` | 基本ルールに忠実に、噛み砕いた説明を意識する（Step1読者向け） |
| `プロンプト設計` / `業務効率化` / `ツール比較` | 「筆者の体験談」を最も色濃く出す。Before/Afterを必ず入れる |
| `Tips・小技` | テンポよく、結論を早く出す。前置きは短めに |
| `ニュース` | 事実部分は客観的に、影響・所感の部分で「筆者」視点を出す |
| `開発者向け` | 専門用語の補足を省略してよい。技術的な正確さを優先しつつ、である調にはしない |
| `AIにキャラクターを与えてみよう` | 例外的に遊び要素・カジュアルな言い回しを許容（文末は基本です/ます調を維持） |

## 11. チェックリスト（執筆後の確認用）

- [ ] 「筆者」視点の実体験が最低1箇所は入っているか

- [ ] 断定しすぎる表現・煽り文句がないか
- [ ] 専門用語の説明過多・説明不足になっていないか（対象カテゴリのレベル感と合っているか）
- [ ] プロンプト・コード例はコピペしやすい形になっているか
- [ ] 9章の言い回しの癖を潰したか（特に「〜ではないでしょうか」が2回以上出ていないか、締めが「ぜひ試してみてください」で終わっていないか）
- [ ] 9章の「固有性を足す」から最低1つ（試した時点／外れたこと／実測の数字／判断の理由）が入っているか
