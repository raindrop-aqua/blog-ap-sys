## 1. この文書の役割

企画ドキュメントは「いつ開くか」で3つに分かれている。

| 文書 | 開くタイミング |
|---|---|
| [content-strategy.md](content-strategy.md) | 企画の方向性を決めるとき・新しいネタをどこに位置づけるか迷ったとき |
| **article-backlog.md（本書）** | 次に何を書くか選ぶとき・公開順を組むとき |
| [writing-style.md](writing-style.md) | 実際に記事を書いている最中 |

- ネタが増減するたびに本書を更新する。方針レベルの変更（カテゴリの追加、ペルソナの変更など）はcontent-strategy.md側で行う

- ストックの偏りや補充のタイミングは、[content-strategy.md](content-strategy.md)6章の見直しトリガーに従う（ネタ帳の残りが10本を切ったら補充、など）

## 3. 公開順序の依存関係

記事どうしが前提知識や橋渡しリンクでつながっているため、公開順には制約がある。依存を**強い依存**（順序必須）と**弱い依存**（後追いでリンクを足せる）に分けて管理する。

### 強い依存（この順序を守る）

先行記事が前提知識になっており、順序を逆にすると読者が置いていかれる。

| 後続 | 先に公開しておく記事 | 理由 |
|---|---|---|
| 3. プロンプト設計の型（全5回） | 2. プロンプトの基礎体力（全2回） | 型シリーズより前に読んでほしい入門編として設計されている |
| 5. ステップアップ編（全4回） | 3. プロンプト設計の型（全5回） | 型を身につけた読者向けの応用編（明記はないが性質上） |
| 9. 自分のツール・エージェント（全2回） | 8. AIの拡張のしくみ（全4回） | 8はハンズオンを読むための前提知識という位置づけ |
| 8-② 公式Skillsを覗いてみよう | 8-① AIの「指示の与え方」を整理する | ①で学んだ書式と照らし合わせて読む回 |
| 9-② エージェントを作ってみよう | 9-① 簡単なツールを作ってAIに使わせる | ①で作ったツールをそのまま使う回 |
| 10-① セキュリティ第2弾 | 1-① セキュリティ設定を見直そう | 「第2弾」を名乗る以上、第1弾が公開済みである必要がある |
| 10-② AIを利用した設計の方法論 | 1-⑨ コンテキストが溢れるとどうなる？ | コンテキストウィンドウの限界を前提に話を進める |

### 弱い依存（リンクは後追いでよい）

記事末尾の橋渡しリンク。リンク先が未公開でも記事自体は成立する。

| 記事 | 末尾でリンクする先 |
|---|---|
| 1-③ AIは「持っている知識」しか扱えない | 7-① ノートブック機能（手軽な方法）／9-② エージェント（本格的な方法） |
| 1-① セキュリティ設定を見直そう | 10-① セキュリティ第2弾 |
| 1-⑨ コンテキストが溢れるとどうなる？ | 10-② AIを利用した設計の方法論 |
| 5-④ 自分だけのエージェントとして独り立ちさせる | 9-② 本格的なエージェント構築 |
| 6. テンプレート活用術（2本） | 3. プロンプト設計の型シリーズ（相互リンク） |
| 8-① AIの「指示の与え方」を整理する | 冒頭の交通整理から 1-③ ／ 7-① ／ 9-② |
| 7-② 「社外に出せない」現場のためのAI選び | 1-① セキュリティ設定を見直そう（前提となる注意点） |
| 7-④ コードレビューに使えるのはどれ？ | 10-① セキュリティ第2弾（ソースや認証情報を渡すリスク） |

- 弱い依存は「公開時点でリンク先が無ければリンクを省いて公開し、リンク先の公開時に追記する」でよい。リンク先が揃うまで記事を寝かせない
- ただし1-③は橋渡しが記事の締めそのものなので、少なくとも7-①（手軽な方）は先に公開しておきたい

### 順序を組むときの原則

依存関係に加えて、content-strategy.md 4章の投稿戦略から次の制約がかかる。

- 基礎シリーズ（1. 生成AIのきほん）を連続投稿にせず、業務Tips系と交互に挟む
- `開発者向け`（8〜11）はStep1・2の記事の間に挟み込み、連続させない
- `ニュース`（12）は週1ローテーションの枠外。話題発生時に差し込み、月1〜2本を上限の目安とする

## 4. シリーズ企画一覧

1. **生成AIのきほん**シリーズ（`生成AIのきほん`カテゴリ、Step1入口・全9回想定、週1回ペースの合間に差し込む）
   1. AI利用で大事なこと①：セキュリティ設定を見直そう
   2. AI利用で大事なこと②：ハルシネーションとは何か、なぜ起こるのか
   3. AIは「持っている知識」しか扱えない ― 社内情報・ドメイン知識という壁
   4. AIに「このモデルの使い方」を聞いてみよう
   5. プランモードって何？「モード」の違いを理解する
   6. AIが扱えるファイル・形式を聞いてみよう（input / output）
   7. AIは何が得意？ ― モノマネ・要約・比較など、抽象的な「得意技」から自分の業務での使い道を想像してもらう回
   8. AIツールの便利機能、こんな時に使おう ― 各プロダクトが持つ具体的な機能（検索、コードインタープリターなど）と、その使いどころを紹介する回
   9. コンテキストが溢れるとどうなる？AIの「物忘れ」「混乱」現象
   - ※1・2は分量次第で1本にまとめるか、2本に分けるか執筆時に判断
   - ※3は「学習データがいつまでか」という切り口だと検索機能付きAIには合わないため避け、**検索しても出てこない社内情報・ドメイン知識を持っていないことがハルシネーションにつながる**という切り口で書く。記事末尾で「その知識をAIに与えて業務に役立てるには？」として、手軽な方法として7.ツール使い分けシリーズの①（ノートブック機能で自分だけのナレッジを作る）へ、本格的な方法として9.自分のツール・エージェントを作ってみようシリーズの②（エージェントを作ってみよう）へ、レベル別に2本立てで橋渡しする
   - ※1（セキュリティ設定を見直そう）はStep1向けの基本的な注意点。10.開発者としてのAI活用ノウハウシリーズの①でStep3向けの技術的な深掘り版（認証情報・DB接続情報の扱い）を扱うので、末尾で橋渡しする
   - ※9（コンテキストが溢れるとどうなる？）は末尾で、開発者視点の応用編として10.開発者としてのAI活用ノウハウシリーズの②（AIを利用した設計の方法論）へ橋渡しする
   - ※7・8は以前「④できることを聞く／⑧得意苦手／⑨機能で整理する」の3本が似た内容になっていた反省を踏まえて再設計したもの。⑦は抽象的な得意技から使い道を「想像させる」回、⑧は具体的な製品機能を「こう使う」と提示する回、という役割分担にしている
2. **プロンプトの基礎体力**シリーズ（`プロンプト設計`カテゴリ、全2回想定。型シリーズより前に読んでほしい入門編）
   1. 文章を構造化して書く基本 ― 章立て、結論ファースト・PREP法（国・教育によって「構造化された文章」を書く訓練の有無が違うという話も交えつつ、AI向けに限らず伝わる文章の基本を確認する）
   2. プロンプトの書き方の基本（Markdown記法で構造化する）
3. **プロンプト設計の型**シリーズ（`プロンプト設計`カテゴリ、全5回想定）
   1. 要約
   2. 企画書化
   3. 添削
   4. 壁打ち
   5. 役割設定
   - 追加候補: 重み付けを意識してあえて意外な出力を引き出す方法
   - 「要約」回の具体案: 青空文庫など**著作権切れの小説**を使い、AIに要約・ポイント3つ抽出をさせる体験デモ（「つまりそれってこういうことでしょ？」に応えるAIの要約力を体感してもらう。素材は著作権フリーのものに限定する）
4. **AIにキャラクターを与えてみよう**シリーズ（`プロンプト設計`カテゴリ、全2回想定。遊び要素が強くSNSでシェアされやすい入り口コンテンツ）
   1. AIに性格を持たせる？ペルソナ設定でAIの個性・モノマネ力を引き出す
   2. 同じ文章を「映画のヴィラン風」「元気なギャル風」「かわいいキャラクター風」に言い換えてみる（デモ中心の記事）
5. **プロンプト設計（ステップアップ編）**（`プロンプト設計`カテゴリ、全4回想定。`ステップアップ`タグを付与する）
   1. AIにプロンプトそのものを書いてもらう方法
   2. 1回のプロンプト・チャットで終わらない作業をAIにやらせる方法
   3. 複数回のやり取りで生じた矛盾を、より上位のモデルにレビュー・修正してもらう方法
   4. 書いてもらったプロンプトを「自分だけのエージェント」として独り立ちさせる ― 毎回貼り付けなくて済むように、カスタムGPT／Claude Projects／Gemini Gemsなど各AIの「保存して呼び出す」機能に落とし込む（ノーコードの話。コードを書いて外部ツールと連携する本格的なエージェント構築は9.自分のツール・エージェントを作ってみようシリーズの②で扱うので、そちらへ橋渡しする）
6. **業務別活用事例**シリーズ（`業務効率化`カテゴリ、全5回想定＋テンプレート活用術2回）
   1. 議事録
   2. メール
   3. 資料作成
   4. データ集計
   5. 企画立案
   - **テンプレート活用術**（2部構成。カテゴリは`業務効率化`。`プロンプト設計`の型シリーズとも関係が深いので相互リンクする）
     1. 業務別テンプレート集 ― 議事録・メール・提案書などの叩き台テンプレートを配布
     2. 「上手なテンプレートとは何か」を考える回 ― テンプレートは項目を埋めようとするほど冗長になりがち、という課題から出発し、良いテンプレートの条件を探る。執筆時点でのたたき台仮説:
        - 項目名を名詞（「概要」）ではなく疑問文（「誰の・何のための資料か？」）にする
        - 「使わない項目は消してよい」と明記し、全項目を埋める圧力をなくす
        - 項目ごとに分量の目安（「2〜3行で」）を指定する
        - 「AIへの指示テンプレート」と「成果物のテンプレート」を分けて考える
        - ※これらは仮説。実際に書きながら検証し、記事内容を確定させる
7. **ツール使い分け**シリーズ（`ツール比較`カテゴリ、全5回想定）: ChatGPT / Claude / Copilot を業務シーン別に比較する
   1. ノートブック機能で「自分だけのナレッジ」を作る ― マニュアルや資料をまとめて投入し、簡易的なRAG（Retrieval-Augmented Generation。厳密には自前でRAGを構築するわけではなく、ツールが検索して回答に活用する仕組みを代行してくれるイメージ、という補足を入れる）としてチャットで質問できるようにする。ツールごとのノートブック／プロジェクト機能の違いを比較する
   2. **「社外に出せない」現場のためのAI選び** ― 常駐先の制約レベル（全面禁止／社内承認ツールのみ／個人利用は黙認／自由）ごとに、現実的に何が選べるかを整理する回。ツールを横並びにするのではなく、**制約の型を軸にツールを当てはめる**構成にする
   3. **長文要約はどれが強い？** ― 同じ文書を各ツールに投げて比較する
   4. **コードレビューに使えるのはどれ？** ― わざと欠陥を仕込んだ短いコードを、同じプロンプトで各ツールにレビューさせる
   5. **Excel・表データの処理はどれが得意？** ― 同じダミーCSVを渡し、集計・クロス集計・グラフ化を依頼する
   - 追加候補: **無料プランだけでどこまで戦えるか** ― 会社がツールを契約してくれない現場向け。各無料枠で同じ1日の業務を回し、どこで最初に止まるか（回数制限・使えるモデル・添付可否）を見る。ただしプラン内容の変化が速く陳腐化しやすいため、書くなら検証時点を強調し、更新前提で扱う
   - ※②はこのブログでしか書けない切り口（読者と同じ制約の中にいる立ち位置）なので、シリーズの入口に置く。「使えるツールが1つしかない・ゼロに近い」現場の読者を切り捨てず、ツールが選べない場合に何ができるか（社内承認済みツールに寄せる、手元の検証は自宅環境で行う）まで書く
   - ※③は要約の巧拙だけでなく、**投入できる長さの上限**と**貼り付けかファイル添付か**という運用面の差を必ず見る。現場では入力方法の制約のほうが効くため。検証素材は著作権切れの文書か、構造だけ再現した自作ダミーを使い、実物の議事録・仕様書は使わない
   - ※④は仕込む欠陥の種類を分ける（null安全・境界値・性能・命名など）。検出できた数だけでなく、**指摘の粒度**（本質的な指摘か、スタイルの重箱か）と**存在しない問題を指摘してこないか**を見る。末尾は「常駐先のソースを貼れない現場でどう使うか」（構造だけ抽象化して相談する等）に着地させる
   - ※⑤は回答の賢さより、ファイルを直接扱えるか・コード実行環境を持つか・xlsxで返せるかという**入出力の差**が本命。添付が禁止されている現場向けに、テキスト貼り付けで済ませる手順も併記する
   - ※全記事が比較型フォーマット。検証条件と検証時点の明記、優劣が付かないときに無理に順位を付けないことは[content-strategy.md](content-strategy.md)5章の比較型ルールに従う
   - ※比較対象のツール名は書いてよいが、**どのツールが常駐先で承認されていたかは書かない**（導入状況の開示になるため）。[writing-style.md](writing-style.md)4章に従う

開発者向け（Step3現場実践・推進）は項目数が多いため、テーマ別に4つのサブシリーズへ分割する。他シリーズの間に挟み込む形で配置する点は変わらない。

8. **AIの拡張のしくみ**シリーズ（`開発者向け`カテゴリ、概念編・全4回想定）
    - ①の冒頭で、「AIに何かを足す」には2系統あるという交通整理を入れる: **知識を足す**（社内情報などをRAG的に読ませる方向。きほん③、7.ツール使い分けシリーズの①（ノートブック）、9.②の本格エージェントで扱う）と、**機能・ツールを足す**（このシリーズ本題のInstructions/Skills/Agents、MCP）。この地図を示してからSkills/MCPの各論に入ることで、他シリーズで散発的に出てくる「AIに何かを足す」系の記事を読者が迷わず位置づけられるようにする
    1. AIの「指示の与え方」を整理する ― Instructions / Skills / Agentsといった基礎概念、ChatGPT・Claude・Copilotなど各AIでの指定方法・呼び方の違いに加え、実際の書式（SKILL.mdのフロントマター＋Markdown本文という定番構成など）も具体的に紹介する（9.のハンズオン記事より前に読む前提知識として配置。②の公式Skills実例を読み解く土台にもなる）
    2. Anthropic公式のSkills(https://github.com/anthropics/skills)を覗いてみよう ― 実際に公開されているSkillsを、①で学んだ書式と照らし合わせながら読んでみる（概念と書式を、公式の実例で具体的に理解する回）
    3. MCP（Model Context Protocol）とは何か ― AIとツール・データソースをつなぐ標準規格を理解する（①のSkills/Toolsの具体的な実装例という位置づけ）
    4. MCPを使うときの注意点 ― 有効化したMCPサーバー・ツールの一覧は常にAIへ渡されるため、実際には使わなくてもトークンを消費してしまう。必要な時だけONにする運用を心がける
   - ※③④は分量次第で1本にまとめるか、2本に分けるか執筆時に判断
9. **自分のツール・エージェントを作ってみよう**シリーズ（`開発者向け`カテゴリ、ハンズオン編・全2回想定。8を前提知識として読んだ後の実践編）
    1. 簡単なツールを作ってAIに使わせる（例: 天気予報取得ツール）
    2. 簡単なエージェントを作ってみよう（①のツール＋AIで「今日のお出かけプラン」を提案させる）
10. **開発者としてのAI活用ノウハウ**シリーズ（`開発者向け`カテゴリ、実践編・全4回想定）
    1. セキュリティ第2弾：AIに与えてはいけない情報（認証情報・DB接続情報など）― 一般向けの注意点に加え、AIが自発的にDBへ接続・システムへログインしてしまうリスクを扱う
    2. AIを利用した設計の方法論 ― コンテキストウィンドウの限界を踏まえ、仕様を適切な粒度に分解し、互いに影響しないよう設計する（結果として人間にも理解しやすい設計になる、という繋ぎ方）
    3. AIが得意な開発言語はどれ？ ― 学習リソース量が多い言語ほど理解度が高い／AIはソースコードの意味を理解しているわけではない、という前提から、型付き言語の有利さや実行して結果を確認できる環境整備の重要性を考える
    4. 確率論と決定論の使い分け
11. **現場導入・推進**シリーズ（`開発者向け`カテゴリ、マネジメント編・全2回想定）
    1. 現場の生成AI導入レベルを診断してみよう
    2. 現場に生成AIを導入してもらうときのアピール方法
