# コンテンツ戦略設計書

「明日使える生成AI」のブログ運営方針をまとめた設計書。今後の記事執筆・シリーズ企画・投稿計画の拠り所とする。

- 関連ドキュメント: [writing-style.md](writing-style.md)（文体ガイド）、[article-backlog.md](article-backlog.md)（記事ネタ帳・公開ロードマップ）

---

## 1. ブログコンセプト

- **サイト名**: 明日使える生成AI
- **運営背景**: 自社はSES事業を営んでおり、社員は客先常駐でシステム開発・運用の価値を提供している。常駐先ごとに生成AIの導入レベルはバラバラだが、個々の社員が生成AIを使いこなせるかどうかが今後の生き残りを左右するという危機感がある。本ブログはその後押しとして運営する
- **一言コンセプト**: 「明日の現場で、そのまま使える」生成AIの実践知を届け、読者を**AIつよつよ人材**に押し上げる
- **読者にたどり着いてほしいゴール**: 「AIに答えをもらう」（受け身の利用）→「自分の考えをAIに裏付けてもらう・壁打ちする」（能動的な活用）→ ゆくゆくは現場でAI活用を提案・推進できる人材へ
- **差別化ポイント**:
  - 生成AIの一般ニュースをそのまま右から左に流すのではなく、**現場でどう活きるか（会話のタネ・使い方への影響・サービス選定への影響）**まで踏み込んで解説する。ニュースを扱う場合もこの基準を守る
  - 理論より実例。プロンプトの実物、Before/After、手順のスクショを重視
  - ChatGPT / Claude / Copilot など**複数ツールを横断**し、ツールごとの向き不向きも扱う
  - 常駐先によって使えるツール・ルールが異なる前提に立ち、**制約の中でどう工夫するか**という視点を持つ
- **価値の置き方**: 記事の価値は「知識そのもの」ではなく「**知識＋他では得られない価値**」に置く。生成AIの一般知識は生成AI自身に聞けば出てくるため、解説だけの記事は構造的に価値が出ない。このブログが他から得られない価値として提供できるのは次の3つで、**どの記事にも最低1つを必ず含める**
  1. **一次体験** ― 実際に試した結果。うまくいかなかった経験も含む（AIが持っていない情報）
  2. **立ち位置** ― 読者と同じ制約（常駐先ごとのルールの差）の中にいる書き手が書いていること
  3. **選別と順序** ― 何を先に知るべきで、何は今は無視してよいかという地図
- **公開前の一問**: 「**この記事、読者がChatGPTに同じ質問をしたら同等以上の答えが返ってこないか**」を自問する。返ってくるなら、上の3つのどれかが足りていない。記事を書き終えたら必ずこの一問を通す
  - 内容だけでなく**文章そのものがAIの出力に見えないか**も併せて見る。書き方の対処は[writing-style.md](writing-style.md)6〜7章にまとめている

## 2. 対象読者（ペルソナ）

**SES企業に所属し、客先常駐でシステム開発・運用に携わるITエンジニア。** ITリテラシーは一定水準以上（非エンジニアではない）だが、生成AI活用の習熟度には幅がある。

- **下限読者**（ここを外さない）: 「業務での活用を始めたいが、何から手をつければいいか・AIに何を聞けばいいかわからない」層
- **上限読者**: 「もっと活用を深めたい」層
- **サブ読者**: 社内でAI活用の旗振り役をしたい人、客先でAI導入を検討するマネージャー層
- **読む場面**: 業務の合間・常駐先への移動中などにスマホで検索 → 該当記事だけ読んで現場で即実践
- **検索意図の例**: 「生成AI 現場 導入」「生成AI 業務 何に使える」「ChatGPT 使い方 仕事」

読者は2つの独立した軸で位置づける。**この2軸に相関はない**。

### 軸1: 読者の成長ステップ

| 段階 | 読者の状態 | 対応するシリーズ |
|---|---|---|
| Step1 入口 | **自分の業務のどれをAIに渡せるかがまだ見えていない**。使い道を見つけ、仕組み・注意点を理解したい | `生成AIのきほん`、`業務効率化`の棚卸し回、`プロンプトの基礎体力`、`AIにキャラクターを与えてみよう` |
| Step2 活用・壁打ち | 業務でAIを使いこなし、自分の考えの検証・ブラッシュアップに使えるようになりたい | `プロンプト設計`の型シリーズ・ステップアップ編、`業務効率化`、`ツール比較` |
| Step3 現場実践・推進 | 現場でAIを使って開発・運用に組み込んだり、周囲にAI活用を広めたりしたい | `開発者向け`シリーズ全体（特に導入レベル診断・導入アピール） |

- Step1の起点は**使い道の発見**に置く。「仕組み・注意点を理解する段階」だけで定義すると、すでにAIを使っている読者向けの入口になってしまう

### 軸2: 現場の生成AI導入レベル

| 導入レベル | 読者の状態 |
|---|---|
| L0 未導入・全面禁止 | 業務でAIを使う手段がない。個人端末での個人利用のみ |
| L1 限定的 | 社内承認ツールのみ使える／入力できる情報に制限がある |
| L2 自由 | 業務で自由に使える |

- L0でStep3の読者（＝現場に導入を提案したい人）も存在する。「まだ使えていない」を習熟度の低さと取り違えない
- L0・L1の読者にとって、業務での使い方をそのまま書いた記事は「読めるが試せない」記事になる。この層に効くのは**業務外で何を練習しておけば、導入されたとき・提案するときに動けるか**という別種の答えである
- 記事側の手当ては5章の共通ルール（業務利用が前提の記事には、手元・業務外での試し方を添える）に定める。**導入レベル用のタグは作らない**。本文の書き方で吸収する

## 3. 記事シリーズ設計

大カテゴリ（`categories`）を軸に、シリーズとして積み上げていく。カテゴリはサイトのカテゴリー一覧（`/categories/<カテゴリ名>/`）の見出しになり、読者が過去記事を辿る主導線になるため、最初に体系を決めておく。読者全員がITエンジニアという前提のもと、成長ステップに応じて8分類とする。

段階タグ（`tags`に付与）は**カテゴリから自動的に決まる**。下表の「既定タグ」をそのまま使い、記事ごとに考えない。判断が要るのは`プロンプト設計`と`業務効率化`だけで、これらは記事の内容に応じて選ぶ。

| カテゴリ | 既定タグ | 内容 | 記事イメージ |
|---|---|---|---|
| `生成AIのきほん` | `入口` | 安全に・仕組みを理解して使うための基礎知識シリーズ | 「セキュリティ設定を見直そう」「ハルシネーションとは」 |
| `プロンプト設計` | `入口` or `ステップアップ` | 汎用的に効くプロンプトの型・コツ、応用テクニック | 「箇条書き→企画書に整えるプロンプト」「役割設定で回答精度を上げる」 |
| `業務効率化` | `入口` or `ステップアップ` | 職種横断で使える業務シーン別の活用事例。加えて、**自分の業務のどれをAIに渡せるかの棚卸し**（Step1の入口となる回）も扱う | 「業務の棚卸し」「議事録作成」「メール下書き」「資料要約」 |
| `ツール比較` | `ステップアップ` | ChatGPT / Claude / Copilot など横並び比較・使い分け | 「長文要約はどれが強い？」「Excel作業ならこれ」 |
| `Tips・小技` | `ステップアップ` | 単発の小ネタ、時短テクニック | 「ショートカット」「拡張機能」「小ネタ集」 |
| `ニュース` | （記事に応じて） | 新モデル・料金体系・M&Aなど業界の動きを、現場への影響という角度で扱う | 「新モデル◯◯登場、客先での話のタネに」「従量課金化で開発者の使い方はどう変わる？」 |
| `開発者向け` | `現場実践` | 生成AIをツール・エージェントとして組み込む・現場導入を進めるための実践知識 | 「天気予報ツールを作ってAIに使わせる」「生成AI導入レベル診断」 |
| `お知らせ` | （記事に応じて） | ブログ運営に関する告知 | 開設記事など |

- `tags`には段階タグに加え、横断キーワード（ツール名・職種・シーン等）を付与する
- `生成AIのきほん`は「理論解説」ではなく「なぜ気をつける必要があるか・どう影響するか」を実例ベースで語り、ブログ全体の「理論より実例」路線から外れないようにする
- `開発者向け`は、テーマ自体が理論寄り（MCP、設計の方法論、言語ごとの得手不得手など）なため、放っておくと解説記事に流れやすい。**1章の「価値の置き方」を最も強く適用するカテゴリ**と位置づけ、次のいずれかを必ず含める
  - 実際に動かしたコード・設定と、その結果（意図どおり動かなかった記録も価値になる）
  - 運用してみないと気づかない話（例:「有効化したMCPサーバーは、使わなくてもトークンを消費する」）
  - 概念の解説が主になる回は、末尾で「読者が明日その概念をどう使えるか」に必ず着地させる
- `ニュース`は事実紹介だけで終わらせず、必ず「読者の現場・業務にどう影響するか」まで書く。扱うトピックは3類型を目安にする ―（1）**新モデル・新機能の登場**（客先での会話のタネ、いち早く試した所感）、（2）**料金体系の変更**（開発者としての使い方・コスト意識がどう問われるか）、（3）**企業・サービスの買収／統合**（利用中サービスへの影響、今後のサービス選定への影響）
- カテゴリが増えすぎないよう、この8分類で運用する。見直しは6章のトリガー（公開記事20本到達）で行い、それまでは増やさない
- 具体的な記事ネタのストック・シリーズ企画・公開順序は[article-backlog.md](article-backlog.md)で管理する。本書は分類と方針のみを扱う

## 4. 投稿戦略

- **頻度**: 全カテゴリ通算で週1本を目標（無理せず継続を優先）。増やす・落とすの判断は6章のトリガーに従い、その場の勢いで変えない
- **曜日**: 月曜投稿を基本とし、週明けの業務にすぐ使える形で届ける
- **1本あたりの分量**: 3〜5分で読める長さ（見出しは5章の型のとおり3〜5個、具体例を必ず1つ以上）
- **ネタの選び方**: 実際に自分が業務で使って効果があったものを優先し、机上の想像で書かない
- **シリーズの組み方**: 単発Tipsと複数回シリーズを交互に配置し、飽きさせない。`生成AIのきほん`のような基礎シリーズも連続投稿にせず、業務Tips系と交互に挟む
- **開発者向けトラック**: `開発者向け`も他カテゴリと同じローテーションに組み込んでよい。ただしStep3はStep1・2を読んだ後に刺さる内容が多いため、連続投稿はせずStep1・2の記事の間に挟み込む
- **ニューストラック**: `ニュース`は週1ローテーションの**枠外**。話題発生時に随時差し込む速報枠とし、月1〜2本程度を上限の目安にする
- **Tipsトラック**: `Tips・小技`も事前にネタを積まない随時枠だが、`ニュース`と違い**週1ローテーションの中で消化する**。短く書けるため、まとまった記事を用意できない週の埋め合わせに使える
- **導線設計**: 各記事末尾に関連カテゴリ・関連記事へのリンクを置く。シリーズ記事には次回予告を添える。カテゴリを跨ぐ橋渡し記事は末尾で明示的に次に読むべき記事へ誘導する（個別の対応は[article-backlog.md](article-backlog.md)2章の弱い依存）

## 5. 記事フォーマット（型）

記事の骨格はカテゴリによって異なる。まず下表で型を選び、その型に従って書く。

| カテゴリ | 使う型 |
|---|---|
| `プロンプト設計` / `業務効率化` | 標準（ハウツー）型 |
| `Tips・小技` | 標準型の簡易版 |
| `生成AIのきほん` | きほん型 |
| `ツール比較` | 比較型 |
| `ニュース` | ニュース型 |
| `開発者向け` | ハンズオン回は標準型、概念解説回はきほん型を内容に応じて選ぶ |
| `お知らせ` | 型は定めない（ただし共通ルールは守る） |

### 全型に共通するルール

front matterの書式はCLAUDE.mdの「Writing posts」を正本とする。加えて次を守る。

- タイトルは検索キーワードを意識しつつ、「明日使える」感（具体性・即効性）を出す
- 見出しの前に、**冒頭1〜2文で「誰の・どんな悩みを解決する記事か」**を明示する
- 見出しは型のとおりに置く。分量が増えるときは見出しを足すのではなく、記事を分割することを先に検討する
- **業務での利用を前提にした記事には、L0・L1の読者向けに「手元・業務外で同じことを試す方法」を1〜2文添える**（2章の軸2）。実物の業務データを使わずに再現する方法を優先する（同じ構造のダミーを自作する型は[writing-style.md](writing-style.md)4章）。添えられないテーマの場合は、その旨を正直に書く（例:「この手順は業務データがないと再現できません」）

### 標準（ハウツー）型

```markdown
## この記事でわかること（結論を先出し）

## 使うシーン

## 実際のプロンプト・手順

## Before / After（できれば）

## まとめ
```

- `Tips・小技`は前置きを削り、「使うシーン」を省いた3見出し（結論 → 手順 → 補足）の簡易版でよい。テンポを優先する

### きほん型（`生成AIのきほん`、`開発者向け`の概念解説回）

概念を扱う回。理論から入らず、読者が実際に遭遇する困りごとから始める。

```markdown
## こんな場面で困ります（読者が遭遇する失敗・違和感）

## なぜそうなるのか（仕組みを、上の実例に紐づけて説明する）

## じゃあどうするか（明日からの具体的な振る舞い）

## まとめ／次に読む記事
```

- **必ず実例から入る**。「〇〇とは」という定義から始めない
- ただし、**読者にまだ失敗体験がない前提のテーマ**（＝下限読者向けの回）では、冒頭を「こんな場面で困ります」ではなく「**こんな場面で使えます／こんなことができます**」に置き換えてよい。業務でAIを使ったことがない読者には困りごとの記憶がなく、失敗からのフックが効かないため
- 仕組みの説明は正確さより「読者の行動が変わるか」を優先する。厳密さが要る部分は深入りせず、実務で困らない線で止める
- 末尾では、レベル別の次の記事へ橋渡しする（依存関係は[article-backlog.md](article-backlog.md)2章）

### 比較型（`ツール比較`）

```markdown
## 結論（用途別にどれを使うか）

## 検証の条件（いつ・どのモデル/プランで・どんな入力を与えたか）

## 比較結果と所感

## 使い分けの指針
```

- **検証条件と検証時点を必ず明記する**。同じ入力を与えたか、無料プランか有料プランか、どのモデルか、いつ試したか（「2026年8月時点」）。これがない比較記事は信用されないし、モデルは短期間で変わる
- **優劣が付かなければ、無理に順位を付けない**。「どれも大差なかった」も結果として書く
- 常駐先では使えるツールが限られる。「どれが最強か」ではなく**「手元にあるツールでどう戦うか」**に着地させる

### ニュース型（`ニュース`）

```markdown
## 何が起きたか（事実を簡潔に）

## 現場・業務にどう影響するか

## 今、何をすべきか／どう捉えればよいか
```

- 「何が起きたか」で終わらせず、必ず「現場にどう影響するか」まで書く
- 事実部分は出典へのリンクを付ける。推測と事実を混ぜない

## 6. 見直しのトリガー

方針の見直しは「そのうち」では起きない。発火条件を決めておき、条件を満たしたときに該当箇所を見直す。**確認は記事を公開したタイミング**に行う（`ls _posts/*.md | wc -l` で本数を数える）。条件を満たしても**「変更なし」で構わない**。

| 発火条件 | 見直すこと |
|---|---|
| 公開記事10本 | 7章のToDo（アクセス解析・OGP画像）に着手するか |
| 公開記事20本 | **全体棚卸し**。(1) 8分類が実態に合っているか（公開実績0本のカテゴリを畳むか補充するか。随時枠の`Tips・小技`・`ニュース`もストック0は正常だが、公開実績まで0ならカテゴリとして機能していない）、(2) 段階タグが極端に偏っていないか、(3) L0・L1の読者が読める記事が書けているか（5章の「手元・業務外での試し方」ルールが空文化していないか）、(4) [article-backlog.md](article-backlog.md)のストックが枯れていないか |
| 2週続けて公開できなかった | 4章の投稿頻度・ネタの選び方。ペースを落とすか、ストックの積み方を変えるか。落とすこと自体は失敗として扱わない |
| 2027年2月末（開設から半年） | 1章コンセプト・2章ペルソナ。前提が変わっていないか |

- **判断材料の一次情報は社内の反応**。主読者は自社の社員なので、「この記事を現場で使ったか」を数人に直接聞くのが最も早く、PVより濃い。数字が取れないうちは、聞ける範囲で聞く
- 週2本への増量は当面検討しない。継続が最優先で、迷ったら増やさない
