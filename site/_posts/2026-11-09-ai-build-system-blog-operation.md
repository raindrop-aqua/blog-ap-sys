「AIってプロンプトを工夫するだけでしょ」「AIでシステムを作るなんて無理でしょ」と思っている方に向けて、AIでブログの運営を仕組みにした1か月の記録を書きます。完全自動ではありませんが、記事を書いて校閲し、公開するところまでは、2日ほどで動くようになりました。

このブログ自体が、その実例です。使っているのは Claude Code で、Skills（作業の手順書）と Agents（別の目で作業する役）という機能です。ここで言うシステムは、ブログを運営する仕組みのことです。業務システムの開発の話ではありません。

## 「AIはプロンプトを工夫するだけ」で止まっていませんか

筆者は、日記の聞き手を生成AIにしています。聞き手には「ギャル」というペルソナを与えていて、前向きな返事をもらいながらその日のことを話し、日記にまとめてもらいます。2025年10月末から続けています。

「ギャル日記」もプロンプト1つで動いています。ブログの記事づくりも、最初は同じ延長でした。AIに聞き手になってもらい、筆者の体験を引き出します。記事を書くスキル（write-post）を初めて動かしたときは、「来た来た」という感触でした。

日記のプロンプトの延長で、記事の運営まで仕組みにできるのか。試した記録が、この先です。

## 作ったものと、作っていないもの

![記事が公開されるまでの流れ。設計書は筆者が書き、記事は筆者とAIが共同で書く。校閲はAIが担当し、読んで直して push するのは筆者、ビルドと公開は自動](/assets/img/posts/2026-11-09-ai-build-system-blog-operation-flow.png)

このブログは、次の部品で回っています。

- 設計書3本（読者とカテゴリ、公開順、文体）
- スキル3つ（記事を書く、ネタを積む、図を付ける）
- エージェント3つ（ネタの切り口出し、ネタの審査、記事の校閲）
- スクリプト1つ（画像のリンク切れを見つける）と、push から公開までの自動ビルド

記事の中身は、筆者が体験を話します。下書きを読んで直し、GitHub に push するのも筆者です。AIが動くのは、構成、下書き、校閲、ネタの審査、図の作成です。ビルドと公開は自動です。完全自動にはしていません。

初回コミット（8月21日 22:42）から、記事スキルと校閲エージェントができるまでは、約48時間でした。最初の記事は、その夜のうちにコミットして、翌8月24日に公開しました。2日で済んだのは、7月から記事のアイディアを溜めていて、何を作りたいかが先にあったからです。ゼロから2日ではありません。

アクセス計測（9月11日）や画像のチェック（9月21日）は、あとから足しました。仕組みは、2日で完成したわけではありません。

## 考え方は4つでした

作りながら考えたことを、4つに分けます。それぞれ、筆者の場合と、自分の仕事に当てはめるときの問いを書きます。

### 続けられる形を先に選ぶ

筆者の記憶では、最初は社内の SharePoint のサイト機能を使って配信するつもりでした。中身のないダミー記事を先に並べて、カテゴリやタグで束ねてみました。記事というより、ビジネス文書が並んでいるだけに見えました。サイト機能の記事を書く機能も見出しや本文のブロックを積む書き方で、執筆に時間がかかると感じました。

Markdown で書けば記事になる GitHub Pages を知って、ぱちっとハマった感覚がありました。書き上げた記事が push だけで公開されるのを見て、「これなら続けられそうだ」と思いました。AIを使う前に、続けられる環境を選んでいました。

自分の仕事に当てはめるなら、こう問います。「中身を作り込む前に、空のダミーで、続けられる形かを試せないか」。合わなければ、作り込む前に替えられます。

### 意図を先に文章にする

設計書は、記事を書く前に作りました。最初は社内向けに、読者を3タイプに分けていました。公開のブログにするときに、内容別の8分類と、読者の段階を示すタグに書き換えました。一度で正解を書いたわけではありません。

文体ガイドは、Claude に「作ってくれ」と頼んで、ほぼそのまま採用しました。設計書のすべてを、筆者が書いたわけではありません。決めたのは筆者です。

公開のブログにすると、常駐先の情報を記事に書いてしまう不安がありました。この不安は、設計を書いた初日の夜に、設計書へ入れています。文体ガイドの最初のコミットから、20分後です。

記事を書くスキルは、この設計書を読み直す作りです。筆者は体験をそのまま書くだけで、設計書の構成に成形されて返ってきます。日記は、筆者の言葉をそのままにまとめてくれました。ブログの仕組みでは、設計書がフィルタになります。そこに校閲が加わって、任せても大丈夫だという安心感がありました。測ったわけではなく、筆者の体感です。

自分の仕事に当てはめるなら、こう問います。「作りたいものの意図を、AIが読める文章にしてあるか」。最初から正解でなくて構いません。書き換える前提で書きます。

### 任せる範囲と、人が決める範囲を分ける

書く役、ネタを審査する役、記事を校閲する役を、別々にしました。Claude と一緒に記事を書いて、校閲エージェントから指摘をもらう体験は、日記のときとは精度が段違いに感じました。

今回この記事を書くにあたって「書く役、ネタを審査する役、記事を校閲する役」それぞれがどのくらい使われているか、9月21日の時点のセッションログから、それぞれを使った回数を数えました（作ったのに、利用していないのであれば意味がありません）。集計の前に予想を書いてコミットして筆者の予想と実際に使った回数を比べてみたのです。9月21日までに書いた記事は7本です。1本の執筆に、校閲が1、2回入ると思っていたので、校閲エージェントは9回以上と予想しました。実際は6回でした。ネタの切り口を出すエージェントは0回と予想して、実際は2回でした。一番使うと思っていた、記事を書くスキルと校閲エージェントは、予想どおり一番使っていました。予想は外れてしまいましたが、「役」が働いてくれていることを確認できました。

構成とまとめと校閲は、筆者はほとんどAIを信じています。筆者が直すのは、言い回しが、筆者の好む文章のスタイルと違うときです。直したいので、完全自動にはしていません。直す余地があるということは、仕組みに手を入れる余地があるということでもあります。仕組みは、これからも変わっていきます。

自分の仕事に当てはめるなら、こう問います。「どこまでAIに任せ、何を自分で直すか」。直したくなる箇所は、仕組みを変える余地の目印になります。

### 困ったら足し、仕組みでも守る

9月21日にちょっとした事故を起こしてしまいました。記事の本文の画像が表示されないまま公開されたのです。画像のパスに `{% raw %}{{ site.baseurl }}{% endraw %}` という、記事公開時に変換をかける部分に間違いがありました。今回のこのミスをチェックする仕組みは、校閲エージェントにも、ほかにもありませんでした。記事公開プログラム（GitHub Actions）の実行履歴から表示されなかった時間を調査したところ、約10時間画像が表示されていませんでした。

修正した同じ日に、次を足しました。校閲エージェントの検査項目、スキルの注意書き、リポジトリの規則、そして画像のリンク切れを見つけるスクリプトです。スクリプトは、公開のビルドと、PR の時点の両方で回します。指示文とスクリプトの両方で守ることにしました。指示文の修正だけでも防げたかもしれませんが、より確実な方法（スクリプトの追加）でガードレールを構築しました。

穴は、今もあります。9月21日の時点で、記事の末尾に書いた次回予告が公開順を固定してしまう問題を、検査する項目はありません。

自分の仕事に当てはめるなら、こう問います。「事故が起きた時、検査不足を調査したか、それを検査する項目を足したか」。

## できていないことと、条件

- 1人・1リポジトリの運営です。承認もレビューも、他人の目はありません。現場で同じことをするなら、承認の段取りが加わります。
- 完全自動ではありません。言い回しを、筆者が直したいからです。同僚にも、そう話しています。
- 記事の質が上がったかどうかは、測っていません。「精度が段違い」は、筆者の体感です。
- 2日で動いたのは、素材と意図が先にあったからです。

## 明日、手元で試すなら

業務で生成AIが使えない現場でも、設計書は先に書けます。誰に、何を、どんな文体で書くかを、Markdown 1枚にまとめます。

個人のリポジトリがあれば、その1枚を読ませて、記事を1本書かせます。手順を毎回打ち込むのが面倒になったら、その手順をスキルにします。校閲は、別の呼び出しに分けます。筆者は、設計書、記事を書くスキル、校閲エージェントの順に作りました。

まだ分かっていないのは、この仕組みが、1人ではなくチームで回るかどうかです。
